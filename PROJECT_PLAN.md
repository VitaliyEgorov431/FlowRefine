# Исходная расширенная концепция проекта

> Этот документ сохранён как исследовательский контекст. Актуальный план под срок меньше суток и работу без GPU находится в [PLAN.md](PLAN.md).

Дата: 24 октября 2026 года.

Рабочее название: **Constraint-Guided Generation and Refinement of Editable Flowcharts with LLMs and VLMs**.

## 1. Цель и исследовательский вопрос

Создать систему, которая получает текстовое описание процесса, генерирует редактируемую блок-схему, проверяет результат и последовательно исправляет ошибки.

Главный вопрос: **когда совместная программная и визуальная обратная связь улучшает смысловую правильность и читаемость схем по сравнению с каждым видом обратной связи отдельно и дополнительными независимыми генерациями?**

Вклад проекта:

- единое структурированное представление схемы и протокол исправлений;
- программные проверки структуры и геометрии;
- цикл исправления с программным, визуальным и комбинированным критиком;
- воспроизводимый набор задач с эталонными структурами;
- сравнение качества, стоимости и новых ошибок, возникающих при исправлении;
- работающий прототип с экспортом SVG, PNG и JSON.

Улучшение комбинированного метода является гипотезой. Отрицательный результат допустим, если эксперимент корректен и объясняет ограничения.

## 2. Зафиксировать границы до реализации

Основная область: блок-схемы процессов на 6–20 узлов. Типы узлов: начало/конец, действие, условие. Поддерживаются линейные цепочки, развилки, объединение веток и возвратные связи.

Вход: естественный язык. Для основных экспериментов выбрать один язык, например английский. Второй язык можно добавить в демонстрацию, не заявляя проверенного переноса.

Выход: SVG для редактирования, PNG для просмотра, JSON для воспроизведения. Веб-интерфейс — поле запроса, просмотр итераций, замечания, экспорт; создание полноценного графического редактора не входит в основной объём.

Система не обучает большую модель с нуля. Дообучение редактора, другие типы диаграмм, PPTX-экспорт и произвольный дизайн — расширения после завершения основного исследования.

План ориентирован на одного исполнителя. Конкретные модели, локальный/API-режим и денежный бюджет фиксируются после аппаратного пилота. Указание RTX 3060 12 GB в HW4 подтверждает среду той работы, но не гарантирует доступность оборудования для этого проекта.

## 3. Архитектура

Описание процесса → LLM-генератор → Scene JSON → детерминированный рендерер → SVG/PNG.

Scene JSON → программный критик → структурированные замечания.

Исходное описание + PNG → VLM-критик → структурированные замечания.

Описание + текущая сцена + замечания → LLM-редактор → исправленная сцена → повторная проверка.

Отдельный оценщик читает эталон и результаты всех режимов. Эталон, его внутренние идентификаторы и тестовые метрики никогда не передаются генератору, критикам, редактору или правилу выбора финальной версии.

### Представление сцены

- Canvas: ширина, высота, фиксированная тема оформления.
- Node: уникальный id, тип, текст, x/y, ширина/высота.
- Edge: id, source, target, подпись, точки маршрута.
- Общие настройки шрифта, интервалов и стрелок.

На первом этапе использовать простое форматирование и фиксированные шрифты. Модель управляет смысловой структурой и расположением. Рендерер не добавляет отсутствующие этапы или связи.

Правила маршрутизации и переносов текста одинаковы для всех экспериментальных режимов. Если они автоматически исправляют часть геометрии, это документируется и применяется ко всем режимам.

### Протокол исправлений

Сначала редактор возвращает целиком новую сцену: это проще отладить. После стабилизации можно перейти к ограниченному набору операций: add/remove node, add/remove edge, update label, move/resize node, reroute edge.

Каждое изменение сохраняется вместе с исходной версией. При одинаковом коде и сцене рендеринг должен воспроизводиться.

## 4. Этап 0 — постановка задачи и аппаратный пилот

Ориентир: 4–6 часов.

Задачи:

1. Написать одностраничный proposal: задача, исследовательский вопрос, методы сравнения, метрики, границы.
2. Проверить актуальные открытые генераторы и VLM: выбрать по одному основному кандидату на каждую роль и резервному кандидату на случай технических проблем.
3. Проверить генерацию структурированного ответа и визуальную критику на 10 примерах разной сложности.
4. Замерить задержку, расход памяти или стоимость запросов; оценить, читается ли текст на рендерах.
5. Оценить ожидаемое число вызовов для полного эксперимента и определить допустимый бюджет.
6. Зафиксировать используемые версии и условия доступа к моделям. Не менять модели по результатам тестовой выборки.

Результат: proposal, выбранная конфигурация, журнал пилота, предварительный бюджет.

Критерий перехода: можно устойчиво получить и отрисовать сцену; VLM видит подписи и даёт проверяемые замечания хотя бы на части специально испорченных примеров. Если это не работает, уменьшить сложность сцен или сменить кандидата до массовых экспериментов.

## 5. Этап 1 — схема данных, рендерер и первая генерация

Ориентир: 10–14 часов.

Задачи:

1. Создать независимую от модели схему данных и проверки обязательных полей.
2. Реализовать узлы, стрелки, подписи, переносы строк и экспорт SVG/PNG.
3. Подготовить 10–15 вручную заданных сцен, включая ветвления, циклы и длинные подписи.
4. Сделать адаптер вызова генератора: запрос → ответ → разбор → сцена.
5. Реализовать единое ограниченное правило восстановления неправильного JSON. Все такие вызовы учитывать в стоимости и одинаково применять во всех режимах.
6. Сохранять raw output, разобранную сцену, ошибки, изображение и параметры генерации.

Результат: рабочая однократная генерация из текста, CLI-команда запуска и примеры экспорта.

Критерий перехода: все ручные сцены воспроизводимо рисуются; ошибки модели явно фиксируются; невалидные примеры не исчезают из отчёта.

Минимальные полезные тесты: ссылки на существующие узлы, уникальность id, правильность направления стрелок, обработка циклов и совпадение размеров рендера с геометрией сцены.

## 6. Этап 2 — набор задач и независимая оценка смысла

Ориентир: 12–18 часов. Начать параллельно по календарю с этапом 1, без необходимости отдельных агентов.

Предварительный состав:

- 30 development-задач для отладки и настройки;
- 30 validation-задач для выбора промптов и правил;
- 120 отложенных синтетических test-задач;
- 20–30 отдельно составленных человеческих задач для проверки переноса.

Размер можно уменьшить после пилота стоимости; разделение данных и независимость финального теста сохраняются.

Семейства: цепочка, одиночная развилка, несколько развилок, слияние веток, возврат на исправление, сочетание ветвлений и циклов. Сложность определяется отдельно числом узлов, топологией, длиной подписей и явностью текстового описания.

Порядок подготовки:

1. Создать корректный эталонный граф процесса.
2. Получить несколько вариантов естественного описания.
3. Проверить, что описание действительно задаёт все обязательные элементы и не противоречит графу.
4. Зафиксировать допустимые эквиваленты и неоднозначности.
5. Разделить задачи по семействам/шаблонам и исходным процессам, до запуска финальных методов. Перефразировки одного процесса остаются в одном split.

Не ограничиваться переименованием узлов одного графа. Не использовать автоматически написанные описания без проверки соответствия эталону.

Сопоставление результата с эталоном:

- по возможности использовать однозначные названия этапов в контролируемом наборе;
- в свободных описаниях сопоставлять семантически эквивалентные узлы по заранее установленным правилам;
- неоднозначные сопоставления отправлять на ручной разбор, не считать совпадение строк достаточной мерой качества;
- эталонные внутренние id не должны быть доступны модели.

Результат: dataset specification, manifests и splits, эталонные графы, правила сопоставления.

Критерий перехода: метрики правильно оценивают заранее сконструированные пропуски, лишние связи, обратные стрелки и эквивалентные подписи. Проверена подвыборка автоматически созданных описаний; человеческий набор проверен полностью.

## 7. Этап 3 — программный критик

Ориентир: 8–12 часов.

Формальные проверки:

- корректная схема данных;
- существующие source/target;
- уникальные идентификаторы;
- положительные размеры и допустимые координаты.

Геометрические проверки:

- перекрытия блоков;
- выход блоков и текста за границы;
- стрелки через посторонние блоки;
- подписи, перекрывающие блоки или другие подписи;
- расстояние между объектами и чрезмерная длина маршрутов как мягкие показатели.

Графовые диагностические признаки:

- недостижимые узлы относительно начала;
- изолированные элементы;
- подозрительные условия без подписанных исходов.

Эти признаки нельзя автоматически объявлять смысловыми ошибками без учёта запроса. Цикл и пересечение стрелок сами по себе допустимы. Жёсткие нарушения и рекомендации по читаемости хранятся раздельно.

Замечание: type, severity, affected_ids, explanation, suggested_action. Программный критик не использует эталон и не заявляет, что нашёл все смысловые пропуски.

Результат: проверяющий модуль и набор специально испорченных сцен.

Критерий перехода: известные геометрические ошибки обнаруживаются, корректные контрольные сцены не получают ложных жёстких нарушений. Пороговые значения зафиксированы на development/validation.

## 8. Этап 4 — VLM-критик и редактор

Ориентир: 10–14 часов.

VLM получает исходное описание, текущий рендер и чёткую задачу: указать конкретные ошибки с привязкой к видимым элементам. Может сообщать об отсутствии уверенности; общие фразы вроде «улучшить дизайн» не считаются полезным замечанием.

Требования:

- отделять смысловые ошибки от визуальных;
- не выдавать предположение за наблюдение;
- ограничить число замечаний, например пятью наиболее существенными;
- не передавать эталонный граф;
- сохранить исходный ответ критика и результат разбора.

Редактор получает исходный запрос, сцену и замечания. Промпт редактора и параметры генерации одинаковы во всех режимах, кроме самого содержимого обратной связи.

Для комбинированного метода начать с простого объединения замечаний с пометкой источника. Приоритет «смысл → структура → оформление» исследовать как отдельное расширение, чтобы не смешивать эффект двух критиков с эффектом нового алгоритма управления.

Проверить качество самого критика на размеченной подвыборке: долю подтверждённых замечаний, пропуски известных ошибок, случаи ложных требований.

Результат: один работающий цикл исправления для каждого вида обратной связи.

Критерий перехода: ошибки критика и редактора наблюдаемы в логах; можно различить плохое замечание, неверное выполнение исправления и ошибку оценщика.

## 9. Этап 5 — протокол экспериментов

Ориентир: 6–8 часов подготовки плюс время инференса.

Основные режимы:

| Код | Режим |
|---|---|
| B0 | Однократная генерация |
| B1 | Исправление по программным замечаниям |
| B2 | Исправление по VLM-замечаниям |
| B3 | Исправление по обоим источникам |

Основной эксперимент: одна и та же начальная сцена для B0–B3; до трёх раундов исправлений, качество фиксируется после каждого раунда. По возможности два независимых начальных прогона на задачу. Seeds, настройки и версии сохраняются; детерминизм внешнего сервиса не предполагается.

Дополнительные сильные контроли:

- **Детерминированное расположение:** тот же сгенерированный граф, размещённый обычным graph-layout алгоритмом. Показывает, насколько визуальная коррекция полезнее готового способа расположения. Отдельно оценивать содержание и геометрию.
- **Повторные независимые генерации:** сопоставимый бюджет дополнительных вызовов без истории исправления. Если выбирается лучший вариант, правило выбора работает без эталона, фиксируется заранее и его стоимость учитывается.

Не объявлять одинаковое число раундов одинаковой вычислительной стоимостью: VLM-критика добавляет вызовы и визуальные токены. Представить два вида сравнения — качество по раундам и качество по фактической стоимости.

При одинаковой политике обработки ошибок сохранять невалидные попытки и результаты отказов. Основной анализ включает все задачи, а не только успешно отрисованные.

Финальная версия в основном фиксированном протоколе — результат последнего запланированного раунда с общей для всех режимов политикой восстановления невалидного формата. Выбор «лучшей по тестовому эталону итерации» запрещён. Отдельно можно показать oracle-best как явно обозначенную недостижимую верхнюю оценку, но это необязательная часть.

Остановку по отсутствию замечаний и откат ухудшений вводить отдельной абляцией после основного сравнения. Для отката допустимы только признаки, доступные реальной системе; тестовые semantic scores недоступны.

Результат: experiment_protocol.md и конфигурации, зафиксированные до финального теста.

## 10. Метрики и анализ

Основные показатели:

1. **Semantic node/edge precision и recall:** пропущенные и лишние элементы после согласованного сопоставления узлов; направление и подписи веток учитываются.
2. **Полная корректность схемы:** выполнение всех обязательных требований, когда эталон однозначен.
3. **Геометрические нарушения:** число нарушений и доля схем без жёстких нарушений.
4. **Динамика исправлений:** устранённые ошибки, оставшиеся ошибки, новые ошибки после каждого раунда.
5. **Стоимость:** все вызовы, текстовые/визуальные токены при доступности, latency, ошибки сервиса, локальное время и память либо цена API.
6. **Читаемость:** слепое парное сравнение небольшой случайной подвыборки людьми.

Не объединять смысл, геометрию и стоимость в один произвольно взвешенный балл как единственное доказательство.

Статистика: парные различия методов на тех же задачах; доверительные интервалы через bootstrap по исходным задачам. Итерации и перефразировки не являются независимыми наблюдениями. При нескольких прогонах сначала учитывать вложенность прогонов в задачу.

Человеческая оценка: перемешать порядок, скрыть названия методов, заранее определить критерии. Желательно два оценщика; если один — явно указать ограничение. Не поручать итоговую оценку только тому же VLM, который участвовал в исправлении.

Обязательные рисунки:

- смысловая правильность по раундам;
- геометрические ошибки по раундам;
- качество против стоимости;
- результаты по сложности;
- примеры исправления и регрессии.

## 11. Этап 6 — пилот всей системы, затем основной запуск

Ориентир: 5–8 часов анализа пилота; полный инференс оценивается по измерениям.

Сначала прогнать все режимы на 15–20 development-задачах. Проверить:

- первая генерация не решает все задачи без ошибок и не проваливается почти всегда;
- шрифты и подписи читаемы;
- геометрические проверки не конфликтуют с рендерером;
- критик и редактор дают конкретные действия;
- повторный запуск продолжает сохранённый эксперимент;
- финальный объём укладывается в бюджет.

Если исходные задачи слишком лёгкие, менять development-дизайн и заранее зафиксировать более сложный тест. Не выбирать тестовые задачи постфактум по выгоде для собственного метода.

После заморозки конфигурации выполнить основной тест. Исправления кода, влияющие на результаты, требуют версии протокола и согласованного повторения затронутых режимов.

Результат: полные логи, таблицы и изображения, включая неуспешные случаи.

## 12. Этап 7 — демонстрация, отчёт и защита

Ориентир: 10–14 часов.

Демонстрация:

- запрос и выбор режима;
- первая и текущая схемы;
- замечания с указанием источника;
- история итераций;
- экспорт SVG/PNG/JSON;
- сохранённый пример для показа при отсутствии сети.

Отчёт:

1. Задача, мотивация и связь с существующими работами.
2. Архитектура и собственные компоненты.
3. Данные, разбиение и правила оценки.
4. Режимы сравнения и бюджет.
5. Результаты с неопределённостью.
6. Анализ успешных исправлений, регрессий и ошибок критика.
7. Ограничения и воспроизводимость.

Презентация строится вокруг вопроса, метода, честного сравнения и вывода. Число слайдов зависит от выделенного времени защиты. В репозитории: README, инструкции запуска, конфигурации, код, данные или инструкция получения, сырые результаты и скрипты анализа. Публикация репозитория — отдельное действие после подготовки материалов.

Критерий готовности: из сохранённых результатов можно заново построить все таблицы и рисунки; есть полностью воспроизводимый пример от запроса до SVG; выводы соответствуют измерениям.

## 13. Рабочая структура репозитория

```text
src/
  schema/       # Scene, Node, Edge, Feedback
  rendering/    # SVG, PNG, text geometry
  models/       # generator, critic, editor adapters
  validators/   # formal and geometry checks
  pipeline/     # generation/refinement orchestration
  evaluation/   # reference-only semantic scoring
data/
  development/
  validation/
  test/
configs/
experiments/
results/
analysis/
demo/
tests/
docs/
```

Это предлагаемая структура будущей реализации; сейчас создан только план.

## 14. Сроки и приоритеты

Предварительная оценка: примерно **75–110 часов активной работы**, плюс инференс и ожидание вычислений. Это ориентир, а не обязательство; уточняется после пилота и информации о дедлайне.

Возможное распределение на четыре недели:

| Неделя | Основной результат |
|---|---|
| 1 | Proposal, модели, Scene JSON, рендерер, первый прототип, правила датасета |
| 2 | Данные, независимая оценка, программный критик, VLM-критик, исправления |
| 3 | Полный пилот, фиксация протокола, основные эксперименты |
| 4 | Анализ, дополнительные контроли, демонстрация, отчёт, защита |

Если времени меньше: сокращать количество моделей, число вторичных экспериментов и оформление интерфейса. Сохранять независимый тест, сопоставимые начальные условия, учёт стоимости и проверку смысловой правильности.

Обязательное ядро: одна конфигурация генератора/редактора и VLM, четыре основных режима, три раунда, независимый тест, автоматическая и ручная проверка части результатов, экспорт, отчёт.

Следующий приоритет: graph-layout baseline, независимые повторные генерации, повторные seeds.

Дополнительно: learned editor, второй язык, другой тип диаграмм. Добавлять только после закрытия основного вопроса.

## 15. Основные риски и решения

| Риск | Что делать |
|---|---|
| VLM не читает текст | Проверить размер шрифта и рендера на пилоте; ограничить плотность; учитывать цену разрешения |
| Автоматический layout уже решает оформление | Включить его baseline; исследовать смысловые ошибки и реальные случаи пользы критика |
| Генератор слишком слабый/сильный | Выбирать конфигурацию на development; не подгонять финальный тест под желаемый результат |
| Критик придумывает проблемы | Размечать точность замечаний, требовать привязку к элементам, учитывать регрессии |
| Семантический оценщик ошибается | Проверить на ручных изменениях; определить эквиваленты; вручную разобрать неоднозначности |
| Комбинированный метод дороже | Показывать качество против фактической стоимости и независимые генерации как контроль |
| Проект разрастается | Держать один тип схем, один язык и ограниченный интерфейс |
| Генерация синтетики слишком шаблонная | Разделение по процессам и шаблонам, отдельные человеческие запросы |
